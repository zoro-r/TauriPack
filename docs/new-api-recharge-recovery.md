# New-API 充值入账与恢复

微信支付成功与 New-API 额度到账是两个状态。`MemberOrder.status = paid` 仅表示支付成功；`NewApiRecharge.status = credited` 才表示上游明确确认入账并且本地已记录成功。

## 自动处理

- 相同用户、金额、到账额度和远端账户的未过期待支付订单复用已有二维码。不同充值新建订单最少间隔 5 秒，每个用户最多 3 笔待支付充值；复用订单不占用新名额。数据库用户锁与待支付订单的去重键、槽位唯一索引共同约束并发请求，适用于多个服务实例。历史订单没有新增字段，仍参与数量限制和复用判断。
- 充值下单先保存本地 `pending` 订单（包含订单号、支付金额、到账额度及远端用户 ID），再用同一订单号调用微信下单。获取二维码后只更新二维码字段，避免覆盖并发支付回调写入的状态。微信下单或二维码保存失败时保留本地订单并记录订单号和错误，供回调与订单查单核对；不能因请求超时直接删除或关闭订单。
- 二维码未保存且请求曾发出时，重试先查微信：明确不存在才继续使用同一订单号下单；已存在且未支付则先关闭微信订单，再允许新建；支付结果不明时保留订单。订单准备使用独立的数据库租约，防止同时调用微信下单。
- 微信支付回调先验签、解密并核对应用、商户、支付金额、币种及支付流水，再原子保存支付结果。关闭状态只能从 `pending` 更新，不能覆盖 `paid`；有效成功通知允许纠正此前的 `closed`，退款订单不会因重复通知恢复为已支付。
- API 充值回调落库后立即返回成功，不等待 New-API 请求。处理失败通过中间件返回 HTTP 500，使微信能够重试；保存成功后即使进程退出，已支付订单仍可被补偿任务处理。回调原始请求按字节拼接后统一解码，避免网络分块破坏 UTF-8 内容及验签。
- 订单级 `orderId` 唯一索引与 MongoDB 原子状态更新防止回调、轮询和多个服务实例重复发送同一笔充值。
- 查询远端用户失败发生在加额度请求之前，记录为 `failed + retrySafe = true`，允许重试。
- 加额度请求发出后出现网络错误、响应不明确或本地成功状态保存失败，保留 `crediting`，禁止自动再次加额度。
- 数据库连接成功后启动补偿任务，每 30 秒同时扫描两类订单，每类每批最多 20 笔、最多 5 笔并发：待支付订单主动查询微信，补回漏通知的支付；已支付订单补发安全的 New-API 入账。入账只处理尚无记录、`pending` 或 `failed + retrySafe = true` 的订单；已有失败记录至少等待 60 秒再尝试。当前进程批次不重叠，数据库条件更新及入账锁约束跨实例重复处理。
- 充值订单有效期 30 分钟，同时传给微信。过期待支付订单仍占名额，需主动查单并成功关闭微信订单后才释放；明确微信不存在时，还须确认数据库中没有正在下单的请求。网络错误不能作为未支付的证据，不直接删除订单。
- New-API 管理接口请求设置 30 秒 socket 空闲超时。该超时不代表远端执行失败。

微信接收确认与重试规则参考[支付通知文档](https://pay.wechatpay.cn/doc/v3/partner/4012167493)，过期查单与关单参考[Native 支付开发指引](https://pay.wechatpay.cn/doc/v3/merchant/4012791891)。以上订单复用、限频及主动查单目前适用于 New-API 钱包充值，会员套餐和文档页数充值保留原有创建流程。

## 部署

新增 `RechargeOrderGuard` 集合，以及 `MemberOrder` 的两项部分唯一索引。服务启动和充值请求会等待订单索引初始化成功；历史订单没有去重键和槽位，不进入新唯一索引，不会因此删除或改写历史数据。

上线时停止旧服务实例后再启动新版，避免旧下单路径绕过数据库锁。部署后确认索引创建及补偿任务启动成功，再进行真实支付验收。回退前保留新增字段和入账状态，不使用会按超时自动重放不确定入账的旧逻辑。

## 历史订单处理

部署不会自动重放旧 `failed` 或 `crediting` 记录。旧代码可能已向上游加额度，但没有记录成功，重放可能造成重复到账。

管理员需按订单号、支付流水、远端用户 ID、额度及时间核对 New-API 充值/管理日志；不能仅凭当前余额判断是否入账，因为用户可能已经消费，或有其他充值。

复用现有管理员订单同步接口 `POST /api/admin/member/orders/:id/sync` 的 `rechargeResolution` 参数（仍要求管理员权限）：

- `credited`：确认远端已经入账，仅补记本地成功状态。
- `not_credited`：确认远端没有入账，允许本次订单重新执行充值。

处理中记录更新后 10 分钟内拒绝人工修改，避免与正在执行的请求冲突；核对写入采用状态和更新时间的条件更新。等待本身不能证明远端未执行，必须先核对远端记录。

## 验证与边界

运行 `cd apps/basic-server && node --test tests/rechargeOrderCreation.test.cjs tests/wechatPaymentConcurrency.test.cjs tests/wechatNotifyTransport.test.cjs tests/newApiRecharge.test.cjs`，覆盖并发下单、复用与限额、50 次重复回调、关闭与支付竞态、漏回调恢复、HTTP 失败重试响应、原始请求字节处理、上游响应丢失、本地落库失败及人工核对。

测试使用模拟数据库和上游请求，不等于真实 MongoDB 并发压测或微信支付端到端验证。当前调用的上游加额度接口不携带订单幂等键，因此无法仅凭本地状态自动确认跨服务异常请求的结果；这类订单需要核对。要实现这部分完全自动恢复，需要上游支持订单幂等键和按订单查询入账结果。
